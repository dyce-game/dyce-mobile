## ADR-034 · Release and operations setup: build variants, EAS, CI across two repos, monitoring behind flags · 2026-11-23

Context: Phase 5 needs the app to ship, be updated and be watched before any store, cloud, Sentry or PostHog account exists, so everything has to be configuration that works once credentials appear, with no secret in either repository.
Decision: (1) **One `app.config.ts`, three variants** chosen by `APP_ENV` (set per profile in `eas.json`): production keeps `games.dyce.app`, preview and development get `.preview` / `.dev`, their own name and link scheme, so a tester keeps the store app beside a beta, and only production claims the `dyce.games` universal links. (2) **EAS owns build numbers** (`appVersionSource: remote`, `autoIncrement`); the marketing version is `VERSION` in `app.config.ts`, bumped by hand. **OTA updates use `runtimeVersion: { policy: 'fingerprint' }`**, so an update can only reach builds with the same native code, and **channel = profile name**. `updates` is configured only when `EAS_PROJECT_ID` exists (a human step); development builds never take updates. (3) **Public URLs live in `eas.json`; DSN, analytics key and anything secret live in EAS environment variables** (profile `environment` = profile name), never in git; `pnpm release:check` fails on a secret-looking key in `eas.json`, a wrong channel, a changed production bundle id, a staging URL in production, or a permission declared without the library that uses it. (4) **Unused permissions removed** (camera, microphone, photo library, Face ID and biometric were declared but no code uses them: the stores and the privacy answers read the manifest); they come back with the feature. (5) **EAS cannot see the sibling repo** that `@dyce/shared` and `@dyce/games` link to, so `eas-build-pre-install` runs `tools/release/fetch-backend.mjs`, which clones the backend at `BACKEND_REF` (production builds must pin a commit) with a read-only token held as an EAS secret. (6) **Sentry** (`@sentry/react-native`) is required lazily and only when a DSN is built in; no default PII, no screenshots, no user, every event and breadcrumb scrubbed by `monitoring-scrub.ts` using the one shared redactor in `@dyce/shared`. **PostHog without its SDK**: `analytics-core.ts` batches anonymous events to `/batch/` (random per-install id, `$process_person_profile: false`, a runtime guard drops name- or number-like properties), so there is no native module and no code path without a key. (7) **CI** (`.github/workflows`): the app job checks out the backend next to it (repo and ref are variables, a token secret while it is private) and runs format, lint, typecheck, tests and `release:check`; a second job exports the web build, serves it and checks it points at the intended API; EAS build and update are manual workflows that refuse to run without `EXPO_TOKEN`.
Consequences: nothing here has run against Expo, Apple, Google, Sentry or PostHog: the eas-cli flags in the workflows follow eas-cli 16 and must be confirmed once. Adding `expo-updates` and `@sentry/react-native` needs a native rebuild of any existing development client. The listed analytics events are typed but only six are called from screens (BACKLOG). Open for a human: the accounts and credentials in `docs/RELEASE_CHECKLIST.md`. Owner: release-engineer.

## ADR-033 · Sea Battle, Ayo / Mancala and Ludo: a board kit for turn-by-turn 3D games · 2026-11-22

Context: three more 3D async games (ADR-030 is the shot-based pattern) that are not shots: Sea Battle with both players placing at once and a hidden fleet, Ayo and Mancala (one engine, two rule sets) with a sowing that has relays and captures, Ludo with a die the server rolls. They need a scene, a tap-first way to play, a replay of the last move and a held result, but no aim-and-release gesture and no client prediction (every outcome is the server's).
Decision: (1) **`boards/board3d/`** holds what the three share and nothing in `r3f-common/` or the registry changed: `Stage3D` (the canvas in the band between the HUD pieces, the flat picture and a clear message when there is no WebGL, and an overlay slot whose buttons are placed by projecting the scene's own camera, so what you tap is what a screen reader reads), `use-move-replay.ts` (shows each new move once per device through the same per-match "played" counter as the sports boards, so an entry's `holdResult` can reuse `holdsForFinalShot`; Reduce Motion, a move that cannot be shown and a watchdog never hold the game), `controls.tsx` (44pt glass buttons, an arrow pad, a two-way switch), `DieFace.tsx`, `anim.ts`. (2) **No prediction.** The board sends the move, waits for the view and animates the last move from the view alone: Sea Battle replays `view.last`; Ayo keeps the previous view and builds a pure sowing timeline from `last.laps` (tested to end on the engine's own board for thousands of random moves, capped at 7 s however long a relay chain is); Ludo needs no previous view at all (`tokensBefore` rebuilds the board from `last`, tested against the engine for 2, 3 and 4 players). While the roll is on its way the die tumbles without landing; it only ever lands on `last.dice`. (3) **Tap, then confirm, with arrows.** Squares under 44pt (Sea Battle's 10 x 10) are chosen by tapping the scene (a ray onto the water) or by an arrow pad, then Fire / Place; Ayo's pits and Ludo's tokens are real buttons projected over the 3D picture, with a "what this move does" preview taken from the engine's own rules (`predictSow`, `previewMove`); Ludo also has a token strip that says what each move does. (4) **One Ayo board, both rule sets**, chosen by `view.variant`; the Ayo Olopon / Mancala switch on the board shows which rules the match uses. Creating a Mancala match needs a per-match option on the server (docs/BACKLOG.md): until then the server creates Ayo only. (5) Ludo is drawn for 2 to 4 players (`view.players`); the live 3 to 4 player room is not wired (it is a new slug, a Spaces table and a game-server room, not a small step on the card room: docs/BACKLOG.md).
Consequences: a seed is one instance of one instanced mesh (Ayo), Sea Battle and Ludo are a few dozen static meshes drawn only when something changes; none measured on a device. The frame loop is `demand`, so a still board costs nothing. Owner: games-3d-engineer.

## ADR-032 · Groups, bots, message actions, reactions, replies and polls in the app · 2026-11-22

Backend decision and rules (admins, 50 members, friends only, 15-minute delete window, scripted bots with no AI): `../dyce-backend/docs/DECISIONS.md` ADR-038. App side:

- **Screens.** Chat tab: the Groups and Bots filters list real rows (a three-avatar cluster for a group, the two-eyed tile and a BOT tag for a bot; Bots always shows all four). New group (`/new-group`, reached from New chat): a name, a placeholder photo that is not a button, and a friend picker (needs two; you are admin). Group thread (the same `/c/[id]` screen as a person's): header with the cluster, name and "N people" (tap for **Group info**, `/group-info/[id]`: rename, add people `/group-add/[id]`, make admin, remove with an inline confirm, step down, leave with a confirm, Start a Space); the sender's name above the first message of a run and their avatar beside the last; centred system lines; poll cards; a **+** by the composer (Poll `/c/poll`, Start a Space) in place of the games button (games and money are for 1:1 friends). A bot thread has the bot tile, "Practice bot · Free", no receipts, no chat info.
- **Message menu** (`MessageActionsSheet`, design MessageLongPress): long-press, **right-click on web**, or the screen-reader action "Message options". A row of five reactions (GG, HA, !!, ?, L as text chips), the message, then Reply, Copy, Delete for me, Delete for everyone ("N min left") and Report. The list is computed by `availableActions` (pure, tested): nothing on a message still sending, deleted or a system line; no React/Reply in an unaccepted request; Copy only for text; Report only for other people's text or polls, never a bot or a card; Delete for everyone only for your own text or poll inside the window. **Forward and "Turn into a challenge"** from the design are not built (no feature behind them): left out, not dead. Report attaches the one message (`messageId`, new on the Report screen and `reportHref`).
- **Optimistic everywhere it is safe.** Sends and replies use the outbox (a reply carries its quote); reactions, votes and both kinds of delete update the cache first and roll back (or refetch) on failure, with the server's tally replacing the guess. Live events patch the cache: `reaction` and `poll` carry the full tally and keep your own pick, `message_deleted` makes a tombstone or removes the row, `conversation` refetches the group (and drops it if you were removed). A card update (money paid, game turn) keeps its reactions and quote.
- **Copy** uses the browser clipboard on web; on a phone it opens the share sheet (Copy is in it) and is labelled "Share text", because no clipboard module is installed (adding `expo-clipboard` is a BACKLOG one-liner that needs a native rebuild).
- **Typing in a group** says "Someone is typing…": the tracker is per conversation, not per person (BACKLOG).
- **Search** also finds groups and bots by name. The Chat badge counts unread in groups and bots too.
  Not verified on a device; see STATUS.

## ADR-031 · Edge flows in the app: game menu, connection cards, dispute, delete account, data download, Help and legal, space edge states · 2026-11-22

Context: a design audit found these screens unbuilt: GameMenu, GameForfeit, GameOffline, GameIssues, GameDetail, PoolRules, Dispute, DisputeStatus, RoomFull, RoomHostLeft, RoomRemoved, SpaceSearch, BadgeDetail, DeleteAccount, Help (and Settings rows to them), StreakLost. The server side is backend ADR-037. Where the docs and the design disagree the docs won.
Decision:

- **Game menu** (`GameMenuSheet`, from the host header while a match is active): How to play (the registry's rules, plus "How Pool works" in Pool), Report the opponent (the existing Report screen with this chat attached), and Resign. Resign asks once more on a card that states the consequence from the match itself ("Amaka wins and takes the ₦2,000 pot. You lose your ₦1,000 stake. This can't be undone."; in Free "No Dyce Cash moves"), then `POST /matches/:id/resign`; the result screen takes over. It is shown only for a 1v1 running match. **Not in the menu:** the design's "Mute chat reactions" and "Sound and haptics" rows: there is no chat mute API and no game sound or haptics setting to switch (BACKLOG), and a menu row that does nothing is worse than none.
- **GameForfeit** is the resign confirmation, not the design's "you left, 8 seconds to come back" countdown: an async game has no turn timer (`turn_deadline` is unset, BACKLOG) and the server forfeits a live seat only after 60 seconds, so no timer is invented on screen.
- **GameOffline / GameIssues.** Async host: when the match query or a move fails with `network`, an "You're offline" card with Retry now (the game is as it was; a move that did not send can be played again; in Pool "the pot is safe"). Live tables (`LiveIssueOverlay`, pure `liveIssue`): your line `reconnecting` gives "You're offline, the table keeps your seat for 60 seconds"; another seat with `connected: false` and not forfeited gives "Amaka lost connection, waiting up to 60 seconds" with a Keep waiting button that comes back only when the set of absent people changes. The 60 is the server's reconnection window (ADR-022), shown as "up to", with no countdown (the room does not send the deadline).
- **GameDetail** is the drawer's "details" sheet (`GameDetailBody`): How to play / Free & Pool tabs from the registry copy, then **Play free** and **Start a pool**, which open the mode sheet with that mode selected (`initialMode`). The design's record and "Friends who play" tabs need per-game stats the server does not return (BACKLOG). **PoolRules** is `/pool-rules` (from the mode sheet, the details sheet, the menu and Help) with the server's live limits (`GET /games/pool`); the docs' numbers replace the design's (₦100 to ₦20,000, Spaces split winner takes all / 60 40 / 50 30 20, top-up under ₦10,000), and the design's "Free-only mode" switch is left out (not in SPEC).
- **Dispute / DisputeStatus** (`/dispute/[matchId]`): one screen, the form while you can, then the status. Linked from a Pool result ("Dispute this result" while allowed, "See your dispute" after). The status is told as the server works: submitted, waiting for a person, decision; nothing is frozen, so the design's "Pot frozen" step and its 48 hours are not shown (24 hours and the live countdown are).
- **Delete account** (`/settings/delete`), **Download my data** (a Settings row: the web saves a dated `.json`, a phone opens the share sheet with the JSON), **Help and legal** (`/settings/help`, `/settings/legal/[doc]`, `/pool-rules`) are linked from Settings. Terms, privacy notice, community guidelines and responsible play are **DRAFT** (`legal-copy.ts`, a banner on every page): legal review is a human gate (SPEC section 14). Help has no "contact support" button because Dyce has no support channel yet (BACKLOG).
- **Space edge states** (`SpaceProblemView`, pure `space-problem-logic`): the full space (from the join refusal), the host closed it or it timed out, you were removed; each says what happened to your seat fee from `SpaceView.exit`. "Notify me if a seat opens" and "Find another space" (public spaces) are not built: there is no waitlist and no public visibility yet (BACKLOG).
- **SpaceSearch**: the existing Search already finds a space by exact code and your own spaces by name, game or code; this adds the All / People / Spaces chips and rows with the game, who is seated, Free or the Pool fee and a Join or Open pill. Searching all public spaces by name needs public spaces (BACKLOG). **BadgeDetail**: tapping a badge opens a sheet with how to get it and when you got it; progress and "N% of players" are not reported by the server, so they are not shown.
- **StreakLost / the streak saver are not built.** The progress data cannot support them: `streaks.saver_expires_at` is never written and the award trigger resets a broken streak to 1 without keeping the old length, so there is nothing to restore. The design is in BACKLOG with the rule that fits the data (a restore window of the Lagos day after the missed day, for a Free win).
Consequences: the host header has a menu button on active matches; every new screen works in both themes with 44pt targets and labels; the legal text must be replaced before launch. Owner: game-platform-engineer, trust-safety-compliance

## ADR-030 · 8 Ball, Darts, Basketball and Archery: one shared 3D kit, the engine's own numbers on screen · 2026-11-22

Context: four more 3D async games (ADR-020 is the Cup Pong pattern) need a scene, a gesture, a non-gesture way to play, a prediction that the server can correct, a replay of the other player and a held result, each with its own physics (a pool table of 16 balls, a dartboard read at a point, a basket from five spots, an arrow in wind). Writing that four times would repeat the hardest code (the shot life cycle) four times.
Decision: (1) **`boards/r3f-common/` holds only what the four share** and Cup Pong's files are untouched: `shot-flow.ts` (a Plan is one shot's animation with an outcome key, a Playback glides to the server's plan when the key differs; the once-per-device "played" log; `holdsForFinalShot`), `use-shot-flow.ts` (the hook: predict and start at once, correct on the server's answer, replay every unseen shot of the other player in order, hold, watchdog, Reduce Motion skips the animation), `camera-math.ts` (one pinhole camera used by the scene to place the real camera and by the touch layer to turn a finger into a point on the table, the board or the target, and a point into a screen position for the dartboard numbers), `webgl.tsx` (no WebGL context, or a canvas that throws, switches the board to its flat SVG view with a message and the sliders), `BoardFrame`, `hud`, `SliderRow`, `Strip`, `ResultStats`. Each game keeps its own scene, controls, flat view, Art, result extras, logic and tests. (2) **The input is only the engine's integers**: 8 Ball `{angle (centidegrees), power, spinX, spinY}` plus `place` (ball in hand, validated with the engine's own `eightBallCanPlace`) and `call` (the pocket for the 8, chosen with a labelled stepper); Darts the aim point in 0.1 mm; Basketball `{aim, power}`; Archery `{aimX, aimY, draw}` where "Allow for wind" moves the sight by the push the shared flight function reports. Every gesture has a slider or button equivalent. (3) **Prediction is the engine's simulation on the input the device sent** (8 Ball is exact, no random element; Darts, Basketball and Archery lack the server's wobble and tremor, so the picture is corrected with a short glide when the server's landing differs). Replays run the same simulation on the stored `from` table or `applied` input; an 8 Ball replay whose pockets do not match the record is skipped. Archery's flight is drawn from the engine's landing point and flight time with the exact constant-gravity arc, shown 1.7 times slower than real time. (4) **The rooms are fixed dark scenes in both themes** (the design's dark files equal the light ones); results and the rest of the app follow the device. (5) **Free only**: `supports_pool` stays false until a Pool match of each has been played through settlement. (6) 8 Ball has no ball numbers (colours and a stripe band only) and no cue-ball English drawn on the ball beyond the spin pad; Darts numbers are screen text placed by the same camera.
Consequences: about 90 draw calls at most per scene by construction (8 Ball 16 spheres plus the table; Darts one board mesh; Basketball and Archery a few dozen), none measured on a device. A change to a physics constant changes replays of running matches (backend ADR-017). Owner: games-3d-engineer

## ADR-029 · Word Tiles, Anagrams, Mini Golf and Tanks: plain views and react-native-svg, not Skia · 2026-11-22

Context: the stack rule names `@shopify/react-native-skia` for 2D games. As in ADR-018 (Word Hunt) and ADR-026 (Doodle), it is not a dependency, its web build needs CanvasKit loaded asynchronously and copied into the web output, and the browser preview that verifies these boards could not be guaranteed to run it.
Decision: (1) **Word Tiles and Anagrams** are plain React Native views (225 pressable squares, tiles, a rack), with the clock ring as one SVG circle. (2) **Mini Golf** draws the hole from `miniGolfHole()` (the engine's own centimetre geometry, y down) in one memoised `react-native-svg` view (`MiniGolfCourse`), with the ball, guide and replayed path in a second SVG on top; a hole is a few dozen shapes, and the ball is a few frames of state at 30 Hz from the shared simulation's trace. (3) **Tanks** draws the seeded heightmap as one polygon in SVG with tanks, blasts and floating damage; the ground changes as shells land by running the engine's own `tanksCarve` shell by shell. The field is the only place that knows about drawing, so a Skia canvas can replace `MiniGolfCourse` and the SVG inside `TanksBoard` without touching the logic files. (4) **The simulation decides, the screen animates.** Both physics games run the shared `simulate*` on the device only for the animation and the "would it hit" hint-free prediction; the server's answer is final: Mini Golf compares the server's `to` and replays from the server's putt on a mismatch, Tanks shows the server's ground and health once its answer arrives. The aim guides are short hints (Mini Golf: a straight dotted line; Tanks: a no-wind arc), never the simulated path. (5) **The result is held** (`holdResult`) until the last putt or shot has been shown (a per-run `createSeenLog`, with an 8 to 9 second watchdog in the board). (6) **Word Tiles uses the engine's own `wordTilesAnalysePlay` and word list for the live preview.** The server's list may be bigger, so a play the app calls invalid becomes "Try it" rather than a dead button; the server refuses what it does not know and nothing is lost. (7) **Touch.** Word Tiles has no pinch gesture: tap a square on the fitted board or press Zoom (44pt squares, scrolls both ways). Fitted squares are about 22pt (an exception to the 44pt target, stated here); every other control is 44pt or more.
Consequences: not measured on a low-end device; Hermes determinism of the two simulations is covered by the backend's golden scenarios but was not run on a phone. Owner: games-2d-engineer.

## ADR-028 · The board registry: adding a game means filling in one entry file · 2026-11-21

Context: the game host, the result screen and `GameArt` each branched on `gameSlug` (Pig, Word Hunt, Cup Pong), so fifteen renderer sessions working in parallel would have edited the same three files, and the host had no answer for a game it knew about but had no board for. GAMES.md also asks for a rules sheet ("how to play in three bullets" and a Pool line) per game, and the drawer had no place to show one.
Decision: (1) **`src/features/games/registry/`.** `rules.ts` is pure data for all 23 games plus Pig: names, the three bullets, the Pool rules sentence and the Pool minimum (GAMES.md; the server enforces the same figure from `games.pool_min_stake_kobo`, backend ADR-036); it is unit tested (three bullets each, minimums equal GAMES.md, no trademarked names). `types.ts` defines `BoardProps<V>` (`matchId`, `match`, parsed `view`, `players`, `myId`, `yourTurn`, `busy`, `moveFailed`, `onMove(action)`, `onSettled`), `ArtProps` and `GameEntry<V>` (`Board`, `Art`, `parseView`, `mover`, `scoreLine`, `ResultExtras`, `holdResult`, `scroll`). `entries/<slug>.ts` is one file per game (24 files: 23 plus Pig) built with `defineGame`; a game whose board does not exist yet is the stub `defineGame({ slug })`. `index.ts` maps `{ [K in GameSlug]: AnyGameEntry }` (a missing entry is a compile error) and exposes `gameEntry(slug)`, `comingSoonSlugs()`, `isLiveGame`. (2) **The shared screens read the entry.** `GameHostScreen` parses `match.view` with the entry's `parseView`, renders its `Board` (in a `ScrollView` when `scroll`), keeps the host on the board while `holdResult` says so (Cup Pong's last throw), and shows the shell's error line; `GameResultScreen` takes the score line from `scoreLine`, the hero from `Art` (`hero`), extra detail from `ResultExtras`; `GameCard` decides whose move it is from `mover` when a game has one (Word Hunt); `GameArt` renders the entry's `Art` or a felt panel. Pig, Word Hunt and Cup Pong moved onto it through thin adapters in `registry/legacy-boards.tsx` (their own board components are unchanged), so their behaviour is the same. (3) **Not-yet-built games.** An entry with no `Board` shows "Coming soon" plus the rules in dev builds (`__DEV__`) and "Update Dyce to play this game" in production; an unknown slug shows the update message. The drawer lists such games under "Coming soon (dev builds only)", where a tap opens the rules; production lists only what the server offers (which hides a game until its row is enabled). (4) **Rules in the UI.** Every drawer tile has a "How to play" button, and the mode sheet has a "How to play" toggle; both show `RulesSheet` (the three bullets and, when the game supports Pool, its Pool line with the server's minimum). The mode sheet's stake chips are now limited to stakes at or above the game's minimum (`stakeChoices(info, game.poolMinKobo)`), and a counter-offer never goes below it. (5) **Recipe.** A renderer session writes `boards/<Game>Board.tsx`, `<Game>Art.tsx`, `<game>-logic.ts` with its parser and tests, fills in `entries/<slug>.ts`, and adds the backend file `0021_enable_<slug>.sql`; it edits no shared file (docs/ADDING_A_GAME.md lists them).
Consequences: the platform files stop being a merge hot spot; a new capability (a new `BoardProps` field, a new hook on the entry) is a platform change made once by the lead session. Live games (Whot!, Crazy Cards, the party games) keep stub entries so their rules show in the drawer-side sheets; they are still played in Spaces. The registry bundles every board eagerly; if the number of 3D boards makes start-up heavy, switch `Board` to lazy imports in `defineGame` without touching entries. Owner: game-platform-engineer

## ADR-027 · The 3D card table for Whot! and Crazy Cards · 2026-11-21

Context: ADR-022 shipped Whot! on a flat 2D table, ADR-025 put Crazy Cards on the debug table. GAMES.md says both are "3D table". Owner: games-3d-engineer.

- **One table, two games.** `src/features/spaces/tables/` holds a round table with seats around it, your hand fanned in front of the camera, the draw and discard piles, the player to move lit, opponents' hands as fans of backs with a count badge, and a results panel with every hand turned over and, in Pool, each seat's payout (from `LiveState.results`). `TableScreen` gets one branch (`isCardGame`) that replaces both the Whot! table and the debug table for these two games; `SpaceScreen` keeps a finished card table up (as it does for party games) so the panel is seen, and the panel's "See results" (or 25 s) moves on. The old `WhotTable` is not deleted: it is the fallback.
- **Only what the view allows.** `views.ts` parses each seat's `view()` with zod (a view that does not parse is "the table could not be read", never a crash); `model.ts` turns it into one `TableModel` for both games: your cards, the others' counts, the card in play, the draw pile size, whose turn, what is in force (colour or asked shape, pick-two chain, direction), the last event, and every hand only once the game is over. Playable cards come from the engine's own `crazyCanPlay` / `whotCanPlay`; the server still validates every move. 108 + 54 cards and whole games are played through the parsers and the move builders in tests against the real engines.
- **Cards are geometry, not textures.** expo-gl has no canvas and no DOM, so there is no `CanvasTexture` or web font on the phone. Faces are flat polygons built from numbers (`card-art.ts`: a small stroke font for 0-9, +, WHOT, the four marks, the five Whot shapes), turned into vertex-coloured triangles, one body mesh plus one art mesh per side (two draw calls per visible side), built once per face and cached. `polygonOffset` keeps the art above the body without spending depth precision; art meshes draw after all bodies. The same scene runs on the GL surface and in the browser (`r3f.ts` / `r3f.web.tsx`, `flat` colour, no tone mapping).
- **Crazy Cards has its own look, never another game's.** A full-colour card with a big mark for the colour (heart, sun, leaf, drop), so colour is never the only signal; a white number with a drop shadow (dark on yellow for contrast); corner index; a dark "Crazy card" with a four-colour wheel. Names are ours: "Crazy card", "Crazy card, draw four", Skip, Reverse, Draw Two, "Last card!". Whot! follows `design/Card` (paper, maroon).
- **Layout is maths, not eyeballing** (`layout.ts`, tested): a camera behind your seat sized to fit the table to the screen width (portrait) or height; seats clockwise from you (the next player is on your left), 1 to 5 opponents spread along the far side; your hand is laid out in screen terms (card width a share of the screen, overlapped so the hand fits, arc and roll), so it fits any screen and up to 24 cards; `project` places the names and counts (RN views) on the same spots as the 3D seats; `chipLayout` narrows and staggers chips for 5 and 6 seats.
- **Motion** (`director.ts` + `actors.ts`, tested): the shuffle and deal at the start, a played card flying over the table to the pile, draws from the pile into a hand or a fan, a penalty pick, the pile reshuffled into the deck, other hands turning over at the end; special cards pulse the seat they hit (Skip, Draw Two, last card) and the table flips the direction arrows on a Reverse. The director never decides what is true: after every update it reconciles each hand, each fan and the pile with the model, so a dropped line or a joined-late table ends up showing exactly what the view says. The canvas draws on demand (frames only while something moves). **Reduce Motion** makes every move a jump and drops the shuffle and pulses; the banner and the screen reader still say what happened.
- **Last card.** The engine needs `call: true` on the play that leaves one card (and Whot! on the one that goes out). As ADR-022 decided for Whot!, the app always sends it, so nobody is charged two cards for forgetting; the "Last card!" moment is the cue (banner, ring and the seat's tag) when anyone drops to one card.
- **Every move has a non-3D path.** Tapping a card in 3D picks it up, then "Play card" (or the deck to draw); a wild asks for a colour or shape in a normal sheet (with marks and names). The "Cards" button opens your hand as a list (name, "You can play this", a 44pt Play button per row) plus Draw/Pass; the status line and the rule line are live regions with the same words. On the phone a running screen reader makes the list the table by default (React Native Web answers "yes" to everyone, so there the person picks it in the menu); the menu also offers "Use the flat table" to anyone. The 3D canvas is hidden from the accessibility tree and replaced by the labelled seat chips and a table summary. The honest limit: below about 7 cards a hand card's visible strip is 44pt or more on a 390pt screen; beyond that cards can still be tapped but the list is the comfortable way (`handStripPts`).
- **Fallback.** No WebGL (checked once on the web) or a GL context that fails or dies (an error boundary) drops Whot! to the existing flat `WhotTable` and Crazy Cards to the same chrome with the card list as the table.
- **Both themes.** The room is the design's dark room in light and dark (PlayCards and its Dark file are identical); the sheets (chooser, list, menu, results) follow the device theme.

## ADR-026 · The party-game screens: one screen per game, the drawing in react-native-svg · 2026-11-21

The canvas is a white square on every phone so a drawing looks the same to all. The alternative to dragging is a Shapes panel (circle, square, triangle, line, zigzag, star; nine places; three sizes) that sends the stroke in one action. White is the eraser. Guessing is an action with a text box; a "close" guess shows without its text, as the room sends it.

On web, without the sensor or without permission, the screen says so and uses the buttons. Alone in act mode "Got it" asks who guessed (the engine requires it); in heads-up the engine refuses a name, so none is asked. The sign of the accelerometer's z axis differs between devices and could not be checked here: a "Tilt feels backwards? Flip it" switch is shown while tilt is on.
- **Table talk** is offered only where the room would relay it (`talkState` mirrors the backend's `chatAudienceFor`); the server still decides.
Consequences: `use-live-table` and `LiveConnection` carry the `canvas` message; `expo-sensors` is a dependency; the scenes are fixed dark panels in both themes as in the designs (Imposter, Werewolf, Charades), Doodle follows the device theme. Not built: 3D art (cards in perspective, avatars standing at a real table, a campfire scene), a spectator mode, word-pack art.

## ADR-018 · Word Hunt board: React Native views behind a renderer interface · 2026-11-15

Context: Word Hunt is the first real game on the match platform (server side: `dyce-backend/docs/DECISIONS.md`, ADR-019). The stack rule says 2D games use `@shopify/react-native-skia`.

- **Skia is not used for the grid.** `@shopify/react-native-skia` is not a dependency of this repo (nothing in `package.json`, nothing imports it), and adding it means a native module, the CanvasKit WASM for the web preview (a few MB, loaded asynchronously) and a lockfile change that other work shares. I did **not** install it or test it in the Expo web preview. The grid is 16 tiles and a trace line, which plain views draw well, and views give every tile an accessible label for free (a canvas would need a parallel accessibility tree). The board is built from views and a `PanResponder`, and works the same in the browser, on iOS and on Android.
- **Renderer interface.** `WordHuntSurfaceProps` in `WordHuntGrid.tsx` is the contract: letters, the picked `path`, a `tone` for the colour of the path, `size`, `disabled`, `onPathChange` and `onCommit`. The board (`WordHuntBoard`) owns the path, the word preview, the found words, the clock and the score; a renderer only draws and turns touches into paths. A Skia renderer can take the same props and replace `WordHuntGrid` without touching the board or the logic.
- **Input.** Dragging across touching letters (diagonals count, a letter once, sliding back un-picks) adds the word on release; tapping letters one by one and pressing **Add word** does the same without dragging (the alternative for people who cannot or do not want to drag). Every tile is a button with "Letter S, row 1, column 2, picked 3" and an `activate` action, so a screen reader can build a word without touching the grid. Hit-testing only counts the middle of each tile (`cellAtPoint`), so a diagonal slide does not clip a third letter.
- **Touch targets.** The grid is as large as the screen allows, 340pt at most and 220pt at least, so a tile is 77pt on a phone and **48pt at the smallest** size (checked at 360x640). That is the stated limit: below a 220pt grid the tiles would drop under 44pt, so on a very short screen the page scrolls instead of shrinking the grid. Letters on the tiles are scaled with the tile, not with Dynamic Type (they are part of the picture); every other text respects Dynamic Type up to 1.3x.
- **Both themes.** The design draws the play table in dark amber for light and dark alike (`PlayWordHuntDark` imports `PlayWordHunt`), so the table is one fixed dark panel; the header, the intro and the result screen follow the device theme.
- **Simultaneous play.** Both players act at once, so the server's single `currentTurn` only means "the first one still playing". The card and the host use `wordHuntMover()` from the player's own view (are _you_ done?) instead. The card fetches the match for an active Word Hunt only.
- **The round survives leaving the screen.** The server only knows when `start` arrived, so the app keeps `{ startedAt, words }` per match in memory and in secure storage (`use-word-hunt-round.ts`): going back to the chat and returning keeps the clock and the words. When time is up the app sends what it has once, and the **Send words** button retries after an error. The server still enforces the real clock.
- **The client predicts, the server decides.** The dictionary the engine uses is bundled with `@dyce/games`, so the preview says "word" or "not in the word list" instantly and the score under the board is a prediction; the server re-checks every word and the winner is its call.
  Consequences: a new 2D game can follow this shape (board = state + gesture, renderer = drawing). If Skia is added later, only `WordHuntGrid` is replaced. Owner: games-2d-engineer

## ADR-020 · Cup Pong: one scene on R3F native and web, the server owns every throw · 2026-11-19

Context: Cup Pong is the first 3D game (docs/GAMES.md: React Three Fiber; stack rule). The same scene must run on the phone (`@react-three/fiber/native` over `expo-gl`) and in the Expo web preview used for browser checks and the guest web game. The engine adds a release wobble from the seeded RNG, so a device cannot know exactly what its throw will do.
Decision: (1) `boards/r3f.ts` re-exports `Canvas`, `useFrame`, `useThree` from the native entry and `boards/r3f.web.tsx` from the DOM entry (pixel ratio capped at 1.5); the scene, board and logic import only from `./r3f`, so there is one scene. It predicts the throw with `simulateCupPongThrow` on the input it sent (no wobble), starts the ball at once, and when the server's answer arrives with a different outcome it glides the ball onto the path simulated from the server's `applied` input; the cups on the table always end up as the server's. (3) The opponent's throw is replayed once per device from the stored `applied` input against the cups reconstructed from the view (standing cups plus the sunk one, put back where the engine had them); if the simulation does not agree with the recorded result the replay is skipped and the banner alone is shown. (6) A watchdog ends a throw's animation 5 s after it started, so a canvas that never reports (no WebGL, backgrounded app) cannot block the game or the result screen. (7) Free only: `supports_pool` is false until a Pool Cup Pong has been played through settlement.
Consequences: a throw whose prediction differs from the server's shows a small correction; replays need the engine's physics to stay unchanged for a given match (already required by backend ADR-017: version the match if constants change). Draw calls are about 85 and triangles under 8k by construction; no on-device frame rate has been measured. Owner: games-3d-engineer
